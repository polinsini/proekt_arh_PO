# 7. Карта данных и потоки данных

Система «Учебный процесс» использует полиглотное хранилище: пять СУБД, каждая
оптимизирована под свой класс запросов. PostgreSQL является **единственным
источником истины (Master / Source of Truth)**, остальные хранилища содержат
**проекции** мастер-данных под конкретные сценарии чтения.

---

## 7.1. Карта данных по хранилищам

### 7.1.1. Роли хранилищ

| Хранилище | Модель данных | Роль в системе | Что оптимизирует |
|---|---|---|---|
| **PostgreSQL 16** | Реляционная, нормализованная (3НФ) | **MASTER — источник истины**. Вся нормативная модель учёта | Целостность (FK, CHECK), транзакции, агрегатная отчётность |
| **Redis 7** | Key-Value (Hash) | Кэш-профиль студента для быстрого поиска по ключу | latency: O(1) чтение карточки по номеру зачётки |
| **MongoDB 7** | Документы (вложенные массивы) | Агрегатные документы «группа целиком» и «вуз целиком» | Чтение одного документа вместо 5–7 JOIN |
| **Neo4j 5** | Граф (узлы + рёбра) | Сеть связей: обучение, пререквизиты, посещаемость | Обходы, пути, паттерны «кто с кем» |
| **Elasticsearch 8** | Инвертированный индекс | Полнотекстовый поиск по учебному контенту | Релевантность, морфология (russian analyzer), фильтры |

### 7.1.2. Распределение сущностей

| Сущность | PostgreSQL | Redis | MongoDB | Neo4j | Elasticsearch |
|---|:---:|:---:|:---:|:---:|:---:|
| Университет / институты / факультеты / кафедры | ✅ таблицы | — | ✅ `university_hierarchy` (дерево) | — | — |
| Специальности | ✅ | — (в составе хеша строкой) | ✅ (в дереве и в профиле) | ✅ узлы `Specialty` | ✅ `specialty_codes` (метка) |
| Группы | ✅ `student_groups` | — (поле `group`) | ✅ `group_profiles` + дерево | ✅ узлы `Group` | — |
| Студенты | ✅ `students` | ✅ `lab3:student:<card>` | ✅ `students[]` внутри профиля | ✅ узлы `Student` | — |
| Курсы + пререквизиты | ✅ `courses`, `course_prerequisites` | — | ✅ `courses[]` в профиле | ✅ узлы `Course`, рёбра `HAS_PREREQUISITE_FOR` | ✅ `course_code`, `course_name` |
| Занятия (лекции/практики/лаб.) | ✅ `lessons` | — | ✅ `lessons[]` в профиле | ✅ узлы `Lesson`, рёбра `HAS_LESSON` | ✅ **основной документ**: title, description, content_text |
| Расписание | ✅ `schedule` | — | — | ✅ узлы `Schedule` | — |
| Посещаемость | ✅ `attendance` — MASTER, партиционирование по `week_start_date` | — | — | ✅ рёбра `ATTENDED`/`MISSED` | — |
| Запись на курс (обяз./электив) | ✅ `student_courses` | — | ✅ `enrollment` в `courses[]` | ✅ рёбра `STUDIES`/`CHOOSES` | — |

### 7.1.3. Фактический объём (после заполнения)

| Хранилище | Объект | Значение |
|---|---|---|
| PostgreSQL | таблиц / партиций | 13 таблиц + 3 партиции `attendance_*` |
| PostgreSQL | строки | студентов 15, групп 4, курсов 5, занятий 15, расписания 18, посещаемости 65 |
| Redis | ключи | 15 хешей `lab3:student:<card>` (7 полей: full_name, group, specialty, department, email, status) |
| MongoDB | документы | `group_profiles` — 4, `university_hierarchy` — 1 |
| Neo4j | узлы / связи | узлы 60 (Student 15, Group 4, Specialty 3, Course 5, Lesson 15, Schedule 18), связи 137: MEMBER_OF 15, BELONGS_TO 4, STUDIES 23, CHOOSES 12, HAS_LESSON 15, HAS_PREREQUISITE_FOR 3, ATTENDED 48, MISSED 17 (48+17=65 ⇄ attendance в PostgreSQL) |
| Elasticsearch | документы | 15 в индексе `lab3_learning_content` |

**Принцип дублирования:** одна сущность хранится в нескольких формах — форма
выбрана под запросы, а не под хранение. Пример: студент — это строка в PG
(нормализовано), хеш в Redis (карточка по ключу), элемент массива в Mongo
(состав группы), узел в Neo4j (вершина обхода).

## 7.2. Потоки данных (запись и чтение)

### 7.2.1. Запись данных (Write path)

**Правило архитектуры: все изменения совершаются только через PostgreSQL.**
Записи в Redis, MongoDB, Neo4j и Elasticsearch — это производные события
(fan-out), выполняемые приложением после фиксации транзакции мастера.

```
                         ┌──────────────────────────────────────────────┐
                         │                ПРИЛОЖЕНИЕ                    │
                         └──────────────────────────────────────────────┘
   (1) команда записи          (3) fan-out после commit — проекции
        │                              │
        ▼                              ├──► Redis:  HSET / DEL lab3:student:<card>
┌───────────────┐   (2) COMMIT   ┘      ├──► MongoDB: $push/$set в group_profiles,
│ PostgreSQL 16 │ ◄────────────  одним куском дерева
│ (MASTER)      │                       ├──► Neo4j:  CREATE узлов/рёбер (MERGE)
└───────────────┘                       └──► ES:     index / bulk в lab3_learning_content
        ▲
        └── если (3) упало — повтор/очередь; мастер уже истинен
```

**Сценарий W1. Зачисление студента в группу**

1. `INSERT INTO students ...` + `INSERT INTO student_courses ...` — одна транзакция в PostgreSQL. Источник истины обновлён.
2. После commit приложение выполняет fan-out:
   - **Redis** → `HSET lab3:student:234004 full_name ... group ... status ...` — карточка появилась в кэше;
   - **MongoDB** → `updateOne({group: "ИКБО-03-24"}, {$push: {students: {...}}})` — студент добавлен в массив профиля группы; при необходимости обновляется `university_hierarchy.groups`;
   - **Neo4j** → `CREATE (:Student)-[:MEMBER_OF]->(:Group)` + рёбра `STUDIES`/`CHOOSES` по записям на курсы;
   - **ES** → студент в индекс не пишется (он там не индексируется).
3. Ошибка на шаге 3 не откатывает мастер: выполняется повтор. Возможна временная расхлестка (eventual consistency), разрешаемая повтором.

**Сценарий W2. Отметка посещаемости**

1. `INSERT INTO attendance (student_id, schedule_id, week_start_date, status)` — PostgreSQL сам направляет строку в нужную партицию `attendance_YYYY_MM_DD` по `week_start_date`.
2. Fan-out: Neo4j `CREATE (:Student)-[:ATTENDED|:MISSED]->(sc:Schedule)`. Redis/Mongo/ES — не затрагиваются (посещаемость там не кэшируется).

**Сценарий W3. Публикация нового занятия курса**

1. PostgreSQL: `INSERT INTO lessons ...` (+ `schedule` при необходимости).
2. Fan-out:
   - **MongoDB** → `$push` в `lessons[]` всех профилей групп, у которых курс в `courses[]`;
   - **Neo4j** → `(:Course)-[:HAS_LESSON]->(:Lesson)` (+ узлы `Schedule`);
   - **ES** → `PUT lab3_learning_content/_doc/<id>` — индексируются title, description, content_text (анализатор `russian`), метаданные lesson_type, tags, specialty_codes, order_number.

**Сценарий W4. Начальная загрузка (Batch/Seed, реализован в лабораторной)**

Единый сценарий восстановления согласованности всех пяти хранилищ из
init-файлов — `./rebuild_all.sh`: PostgreSQL (DROP → DDL → DML, партиции) →
Redis (FLUSHDB → HSET) → MongoDB (dropDatabase → insertMany) → Neo4j
(DETACH DELETE → CREATE) → Elasticsearch (DELETE index → PUT mapping → _bulk).
Скрипт идемпотентен и фактически является процедурой полного ресинхрона
проекций с мастером.

### 7.2.2. Чтение данных (Read path)

**Правило архитектуры: каждый тип запроса идёт в то хранилище, чья модель
под него заточена.** Redis/Mongo/Neo4j/ES читаются напрямую как проекции;
при промахе кэша или отсутствии проекции — обращение к PostgreSQL.

```
  Запрос клиента                     Хранилище-исполнитель
  ──────────────                     ─────────────────────────
  «карточка студента 231004»   ───►  Redis  HGETALL lab3:student:231004   (O(1), ~1 мс)
        │ промах (нет ключа)
        └──────────────────►   PostgreSQL: JOIN students+groups+specialties
                                       → восстановить хеш → ответ + HSET (cache-aside)

  «вся группа ИКБО-03-24»      ───►  MongoDB findOne({group:"ИКБО-03-24"})
                                       (студенты + курсы + занятия одним документом)

  «структура института»        ───►  MongoDB university_hierarchy (1 документ)

  «поиск по конспектам: kubernetes» ─► ES  match content_text + фильтры
                                       (релевантность, морфология, подсветка)

  «путь пререквизитов к 09.DEV» ───►  Neo4j MATCH path = (a)-[:HAS_PREREQUISITE_FOR*]->(b)

  «кто прогулял вместе с X»    ───►  Neo4j (X)-[:MISSED]->(sc)<-[:MISSED]-(other)

  «отчёт: посещаемость группы за месяц» ─► PostgreSQL: агрегат по партициям attendance
```

**Сценарий R1. Профиль студента по номеру зачётки (cache-aside)**

1. Приложение: `HGETALL lab3:student:231004` — попадание → ответ за ~1 мс, PostgreSQL не участвует.
2. Промах → сборка карточки из PostgreSQL (`JOIN` students → student_groups → specialties → departments) → ответ клиенту → `HSET` в Redis для последующих чтений.
3. Инвалидация: при изменении студента (сценарий W1) приложение перезаписывает/удаляет ключ — устаревшее значение не живёт дольше одной записи.

**Сценарий R2. Карточка группы (агрегат)**

1. `db.group_profiles.findOne({group: "ИКБО-03-24"})` — состав группы, её курсы с типом зачисления и все занятия возвращаются одним документом (0 JOIN).
2. Эквивалент в PostgreSQL потребовал бы 4–5 таблиц; это и есть цена/выгода денормализации.

**Сценарий R3. Полнотекстовый поиск по учебному контенту**

1. Приложение: `GET lab3_learning_content/_search` c `match` по `content_text`/`title`/`course_name` + фильтры-термины по `lesson_type`, `specialty_codes`, `tags`.
2. Инвертированный индекс и русский анализатор возвращают релевантный список; результат — ссылки на `lesson_id`/`course_code`, первичные данные при необходимости добираются из PostgreSQL.

**Сценарий R4. Графовые обходы**

1. Цепочка пререквизитов курса, «одногруппники-соученики», «кто был на паре, когда студент X отсутствовал» — запросы-паттерны к Neo4j.
2. Данные рёбер согласованы с `student_courses` и `attendance` мастера.

**Сценарий R5. Отчётность и аналитика**

1. Групповые агрегаты, срезы посещаемости по неделям, исторические отчёты — только PostgreSQL: транзакционная целостность + партиционирование `attendance` по `week_start_date` (каждая неделя — отдельная партиция, старые отсекаются без DELETE).

### 7.2.3. Консистентность и обоснование

| Аспект | Решение |
|---|---|
| Источник истины | только PostgreSQL; остальные хранилища — перестраиваемые проекции |
| Транзакционность | атомарна лишь запись в мастер; fan-out — best-effort с повторами |
| Модель согласованности | eventual consistency для проекций; окно расхождения ограничено одним fan-out |
| Восстановление согласованности | полный ресинхрон `rebuild_all.sh` (идемпотентный seed всех 5 хранилищ) |
| Почему не распределённая транзакция | 2PC по пяти разнородным СУБД дал бы недоступность ради согласованности копий; для read-оптимизаций это избыточно |
