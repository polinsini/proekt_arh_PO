## 2. Текст рассказа (что говорить)

**Вступление.**
«Проект — предметная область университета: университеты, институты, факультеты, кафедры, специальности, группы, студенты, дисциплины, занятия, расписание и посещаемость. Данные разнесены по пяти хранилищам по принципу Polyglot Persistence: PostgreSQL — нормализованный мастер-источник и транзакционные данные; Neo4j — граф связей студентов и курсов; MongoDB — составные документы «профиль группы» и иерархия вуза; Redis — кэш профилей студентов по ключу «зачётка»; Elasticsearch — полнотекстовый поиск по содержимому занятий. В этой практической работе я доработала модель данных: вынесла связь «специальность–дисциплина» в отдельную таблицу многие-ко-многим, добавила таблицу логических связей между дисциплинами, уточнила атрибуты групп, курсов и зачислений и расширила партиционирование посещаемости до полного семестра.»

**PostgreSQL.**
«Ключевое изменение: семестр и признак электива раньше были атрибутами курса, но на самом деле они относятся к учебному плану конкретной специальности — одна и та же дисциплина для одной специальности обязательная, для другой по выбору. Поэтому я создала таблицу `specialty_courses` со связью многие-ко-многим: составной первичный ключ (specialty_id, course_id), CHECK-ограничения на семестр и тип дисциплины. Старые столбцы `courses.semester` и `courses.is_elective` перенесены туда и удалены, у курсов вместо них теперь текстовое описание. Вторая новая таблица — `course_relations`: типизированные связи между дисциплинами (prerequisite, related, continuation) с запретом самосвязи и запретом дублей. В группах появился `enrollment_year` с контролем согласованности номера курса и года поступления, а в зачислениях студентов — семестр изучения; тип зачисления контролируется триггером: он обязан совпадать с типом дисциплины в учебном плане специальности студента. Посещаемость партиционирована по диапазону `week_start_date`, теперь 16 недельных партиций — весь осенний семестр, запись автоматически попадает в партицию своей недели. Всё выполнено миграцией без удаления данных.»

**Neo4j.**
«Граф зеркально повторяет новую модель. Учебный план — типизированные рёбра `PLAN_INCLUDES` со свойствами semester и course_type: видно, что одна дисциплина входит в планы нескольких специальностей. Связи дисциплин — рёбра PREREQUISITE_OF, CONTINUATION_OF, RELATED_TO. Зачисления студентов — STUDIES для обязательных и CHOOSES для элективов, тип зачисления соответствует учебному плану.»

**MongoDB.**
«Здесь документы композиция: профиль группы одним документом — студенты, учебный план с семестрами и типами, занятия. Появились поля enrollment_year и course_number, новая коллекция course_relations, а иерархия вуза хранит группы объектами с годом поступления.»

**Redis.**
«Кэш профилей студентов: ключ — номер зачётки, значение — hash. Добавлены поля enrollment_year и curriculum — персональный учебный план студента с семестрами и типами дисциплин.»

**Elasticsearch.**
«Полнотекстовый индекс содержимого занятий. Документы дополнены кодами связанных дисциплин: prerequisites, продолжения и связанные курсы — теперь по лекции можно найти и её место в учебном плане, и связанные дисциплины.»

**Согласованность.**
«Все хранилища сходятся по счётчикам: 1000 студентов, учебный план 20 строк, обязательных зачислений 1884, элективов 752, связей дисциплин 8, 16 партиций.»

## 3. Терминальные команды (если препод просит «живой SQL/Cypher»)

### PostgreSQL (psql)
```bash
docker exec -it practice01-postgres psql -U admin -d practice_db
```
```sql
-- 1. Новые таблицы
\d specialty_courses
\d course_relations

-- 2. M:N: одна дисциплина в нескольких специальностях
SELECT c.code, count(*) AS специальностей, string_agg(s.code, ', ') AS где
FROM specialty_courses sc JOIN specialties s USING (specialty_id)
     JOIN courses c USING (course_id)
GROUP BY c.code ORDER BY специальностей DESC;

-- 3. Связи дисциплин (8 строк, 3 типа)
SELECT * FROM course_relations ORDER BY relation_type;

-- 4. 16 партиций
SELECT * FROM pg_partition_tree('public.attendance');

-- 5. Автоматическое распределение по партициям
INSERT INTO attendance (student_id, schedule_id, week_start_date, status)
SELECT min(st.student_id), min(sc.schedule_id), DATE '2026-12-09', 'attended'
FROM students st, schedule sc;
SELECT tableoid::regclass AS попала_в_партицию FROM attendance WHERE week_start_date = DATE '2026-12-09';
DELETE FROM attendance WHERE week_start_date = DATE '2026-12-09';

-- 6. Негативные тесты (каждый INSERT должен упасть с ошибкой)
INSERT INTO course_relations (source_course_id, target_course_id, relation_type) VALUES (1, 1, 'related');        -- самосвязь: CHECK
INSERT INTO specialty_courses VALUES (1, 5, 0, 'elective');                                                       -- semester=0: CHECK
INSERT INTO student_courses VALUES (1, 4, 'mandatory', 6);                                                        -- не по плану: триггер

-- 7. Сводка
SELECT count(*) FROM specialty_courses;   -- 20
SELECT enrollment_type, count(*) FROM student_courses GROUP BY enrollment_type;  -- mandatory 1884 / elective 752
```

### 4.2 Neo4j Browser: http://localhost:7474
Вход: `neo4j` / `mysecretpassword`. Выполнять по одному (запрос → граф):
```cypher
// Учебный план M:N — визуально видно: одна дисциплина в нескольких специальностях
MATCH (s:Specialty)-[p:PLAN_INCLUDES]->(c:Course) RETURN s, p, c

// Связи дисциплин (компактный наглядный граф)
MATCH (a:Course)-[r:PREREQUISITE_OF|CONTINUATION_OF|RELATED_TO]->(b:Course) RETURN a, r, b

MATCH (st:Student {record_book: '01001'})-[r:STUDIES|CHOOSES]->(c:Course) RETURN st, r, c

// Счётчики связей
MATCH ()-[r]->() RETURN type(r), count(*) ORDER BY count(*) DESC
```

## 6. Вероятные вопросы препода и ответы

**Почему semester перенесён из courses в specialty_courses?**
Потому что семестр преподавания зависит от специальности, а не от дисциплины как таковой. Это устраняет аномалию: раньше курс мог преподаваться в разных семестрах разным специальностям, но хранил только один семестр.

**Что даёт составной первичный ключ (specialty_id, course_id)?**
Гарантирует одну запись плана на пару «специальность–дисциплина» и реализует M:N: course_id может повторяться с разными specialty_id — одна дисциплина в нескольких планах.

**Как работает триггер в student_courses?**
BEFORE INSERT/UPDATE: функция находит специальность студента через students→student_groups, берёт course_type из specialty_courses и либо пропускает строку (типы совпали), либо вызывает исключение. Проверено: попытка зачислить студента ИВТ на электив как обязательный падает.

**Почему 16 партиций и почему RANGE?**
16 недель = один осенний семестр 2026/27 (понедельники 2026-09-07 … 2026-12-21). RANGE по week_start_date выбран, потому что запросы к посещаемости всегда по диапазону недель: PostgreSQL отсекает лишние партиции (partition pruning). Составной PK (attendance_id, week_start_date) обязателен: ключ партиционированной таблицы должен включать столбец партиционирования.

**Как обеспечена согласованность между БД?**
PostgreSQL — master; остальные хранилища — проекции, формируемые детерминированной генерацией по той же формуле из init-скриптов. Счётчики совпадают (таблица выше). В реальной системе синхронизацию делали бы событиями/CDC.

**Не удалили ли данные при миграции?**
Нет: миграция (migration_practice3.sql) идёт в одной транзакции, данные переносимые поля (semester, is_elective) сначала копируются в specialty_courses, и только потом столбцы удаляются. Существующие строки, ключи и связи сохранены.
